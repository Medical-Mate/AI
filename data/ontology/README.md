등급은 **환자에게 보이는 단계**다. 그래프 깊이가 아니다. 세부 안쪽(힘줄⊂근육⊂돌림근띠)은 그대로 둔다.

| 2 앵커 | 환자가 말하는 단위. 별칭은 여기만. 상부 **하나**에만 닿는다 | 넓히기 | 디자이너 인체도 부위 | 9개: 앞면 머리·목·가슴·배·팔·다리, 뒷면 허리·엉덩이, 탭 전신·피부 |

### 3등급의 두 층 — 환자가 누르는 것과 차트에 적히는 것은 다르다

| kind | 무엇 | 누가 쓰나 | 예 | 지금 |
|---|---|---|---|---|
| `surface` 표면 구역 | 환자가 인체도에서 누르는 위치. 앵커의 직접 자식 | 진료 전 카드 SITE 축 | 팔 → 어깨, 목 안(목구멍), 아랫배 | 25개, 앵커당 2~6 |
| `structure` 구조 | 차트에 적히는 해부 구조. 깊이 자유 | **나중 단계** — 진료 코드·병명이 나왔을 때 어느 부위인지 풀어 주기. 진료 전 카드에서는 쓰지 않는다 | 돌림근띠, 앞십자인대, 무릎, 어깨 | 40개(팔·다리 아래만). 앞십자인대 → … → 무릎 → 다리 |

- 환자는 돌림근띠를 고를 수 없다. "팔"을 누르고 "어깨"를 고른다. 좌/우는 팔·다리에서는 누른 점(양쪽에 하나씩)으로, 눈·귀 같은 구역은 확대 화면의 좌우 점으로 정해진다
- 구역 축은 앵커마다 다르다. 팔은 어깨→손 세로, 허리·엉덩이는 가운데/옆/엉덩이, 머리는 눈/귀/코/입. 전신 통일 안 한다
- `view`: 인체도 앞면(front) / 뒷면(back) / 화면에 없음(none). 뒷면에는 허리·엉덩이 한 점. 디자이너 이미지 = 앞 1 + 뒤 1 + 부위 확대 7
- 2026-09-04 통합(이미지 장수 줄이기): 어깨·팔꿈치·손 → 팔, 무릎·발목·발 → 다리, 허리+엉덩이 → 허리·엉덩이(뒷면). 어깨 앞/뒤·무릎 안/바깥 방향 구역은 제거. 위팔·아래팔·허벅지·종아리는 팔·다리 이미지가 전체라 생긴 칸
- "목"은 둘이다: 목 안(삼킬 때·기침) / 목 뒤·옆(근육·뼈). 환자는 같은 말로 부르니 구역에서 가른다
- 위치 없는 증상(발열·오한·피로)은 앵커 「전신」. 구역 없음. UI는 사이드 탭
- 뺀 것(2026-09-04 결정): 치아·치과(연결하지 않음), 두피(피부 탭으로), 사타구니. 엉덩이는 구역 없이 앵커만 누른다
- 앵커 「피부」(2026-09-04): 마네킹 구역이 안 맞는 피부 증상. 구역 없음, 사이드 탭, 상부는 전신 묶음. 위치는 마네킹 앵커로 따로 받는다

### 진료과 안내 — `departments` (docs/decisions/2026-09-04-department-guidance.md)

- 부위 노드의 속성이다. **구역에 값이 있으면 구역, 없으면 앵커** — 이 대체 규칙은 소비자(카드 export)가 적용한다. 로더는 값을 그대로 노출만 한다
- 복수는 `;` 구분. 순서에 의미 없음. 괄호 병기 항목도 전부 들어 있다(아랫배: 내과;소화기내과;산부인과;비뇨의학과)
- 로더는 고르지 않고, 정렬하지 않고, 증상 축을 참조하지 않는다. 테스트가 소스 코드를 검사해 강제한다
- **우리 콘텐츠다. 인용이 아니다.** `departments_source` = "팀 결정 2026-09-04, 의료인 자문 확인 전". 값이 있으면 출처가 필수(로더 검증)
- 진료과 값의 유일한 출처는 `manual/nodes.csv`. 구조 노드(무릎·어깨 포함)에는 값이 없다(로더 검증)
- 가슴은 응급 안내가 진료과보다 먼저다. 그 순서는 카드 쪽 책임이고 여기서는 값만 든다
- 결정 문서 v1 표와 다른 곳: 입은 치과를 병기하지 않는다(치과 미연결 결정). 문서 갱신은 메인 체크아웃에서
- 자문 회신 시 표 전체 재검토
- `laterality`: 좌/우를 물을 노드인가. 노드를 좌우로 쪼개지 않는다(양쪽 표현 위해)

### 두 층의 연결 — `located_in` (구조 → 구역)

| 방향 | 예 | 성격 | 판정 |
|---|---|---|---|
| 구역 아래에 **무엇이 있나** | 어깨 앞 아래: 위팔두갈래근 긴갈래 힘줄, 관절주머니 | 해부학 사실 인용 | 한다. `structures_under()` 전체·이름순·순위 없음 |
| 구역이 아프면 **무엇이 원인인가** | 어깨 앞 통증 → 힘줄염 | 감별 | 하지 않는다. API 없음 |

- 엣지에 `source`가 비면 조회에서 빠진다. **지금은 0개.** 의료인 자문·출처 확보 후 채운다

- 상부는 부위마다 하나만. 어깨는 상지에만 둔다(UBERON은 가슴 띠로도 걸치지만 인체도는 한 곳만 칠한다)
- 좌/우는 등급이 아니라 속성으로 (미구현)
- 로더가 세 규칙을 로드 시 강제한다. 위반하면 `OntologyError`

```
[1 상지] → [2 어깨] → 어깨관절 → 오목위팔관절 → 오목테두리(관절와순)
                   → 돌림근띠 → 가시아래근 → 가시아래근힘줄
                   → 어깨뼈 → 봉우리
```

## 로더 (2026-09-04)

```python
from medimate.ontology import load_ontology
onto = load_ontology()                 # data/ontology 기본. 검증 실패 시 OntologyError
onto.widen("UBERON:0003671")           # ACL → (term, anchor=무릎, region=하지, path)
onto.lca(["UBERON:0003671", "MAN:001"])  # {무릎관절}
onto.snapshot_id                       # CSV 해시 12자. Provenance.ontology_snapshot에 쓸 값
```

- `part_of`·`is_a` 둘 다 위로 탄다. ACL은 is_a로만 십자인대 계열을 지나므로 part_of만 타면 앵커에 못 닿는다
- 자손 조회(내려가기)는 두지 않는다. 좁히기는 감별이다 (`docs/ai-design.md` §3)
- 같은 거리에 앵커가 둘이면 `AmbiguousAnchorError`. 데이터가 정해야 할 일을 코드가 임의로 고르지 않는다
- `lca(무릎쪽, 어깨쪽)`은 빈 집합(상부가 다르고 상부 위는 없다). `lca(무릎 구역, 발목 구역)` = 「다리」(같은 앵커)
- `zones(앵커)` 구역 목록(CSV 순서), `anchors_in_order()` 앵커 9개(앞면 6 → 뒷면 1 → 사이드 탭 2), `structures_under(구역)`

## 확인된 것

- **partonomy가 실제로 돈다.** ACL → 십자인대 → 무릎관절 인대 →(part_of)→ 무릎관절 →(part_of)→ 무릎 →(part_of)→ 다리
- **SNOMED CT ID(SCTID)가 xref로 붙어 있다** — 40개 중 23개.
  **SNOMED CT 라이선스 없이도 ID 매핑 경로가 확보된다.** FMA·UMLS·MeSH·NCIT도 같이 붙는다
- 규모가 설계와 맞는다 — 무릎 19 / 어깨 21. `docs/ai-design.md`의 "30~50개"와 일치

## ★ 중요 — **UBERON만으로는 임상적으로 불완전하다**

UBERON은 **다종(multi-species) 비교해부학** 온톨로지다. 사람 임상에서 흔한 구조가 빠진다.
`source` 컬럼이 `수동(...)`인 **11개**가 그것이다.

| 빠진 것 | 사유 |
|---|---|
| **내측·외측 측부인대(MCL/LCL)** | **UBERON에 아예 없다.** 무릎 통증에서 ACL만큼 흔한데 |
| **반월판(내측·외측)** | `meniscus`는 있으나 `part_of skeletal joint` — **무릎 하위가 아니다** |
| 무릎 관절연골 | 없음 |
| 견봉하 점액낭, 위팔두갈래근 긴갈래 힘줄 | 없음 |
| 어깨뼈·빗장뼈·위팔뼈·봉우리 | UBERON에선 `pectoral girdle` 하위라 **어깨 subtree 밖** |

**이게 나쁜 소식이 아니다.** 30~50개 규모면 손보강이 충분히 가능하고,
**"기존 온톨로지가 임상적으로 불완전하다"는 사실이 우리가 만드는 것의 정당성**이 된다.
보강분이 곧 고유 자산이다.
