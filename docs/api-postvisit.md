# 진료 후 기록 API — 백엔드 연동 계약 (v1, 초안 · 2026-09-07)

와이어프레임 1p(진료 후 메모) → 1q(자동 분류 결과) → 1q-2(수정) → 1r(재방문 일정).
AI 서버는 무상태다. 메모 하나를 받아 **4묶음 카드**로 돌려주고 아무것도 기억하지 않는다. 저장은 백엔드.

## 한 번에 끝나는 요청 — `POST /v1/postvisit/memo`

```json
{
  "memo": "위염 초기라고 하셨어요. 혈액검사 했고 결과는 다음에 알려준대요. 약은 2주분이고 커피랑 매운 거 줄이래요. 2주 뒤에 다시 오라고 하셨어요.",
  "visit_date": "2026-09-12",
  "clinic": "서울OO병원 내과",
  "previsit_anchor_id": "ANC:004",
  "request_id": "r-77"
}
```

| 필드 | 뜻 |
|---|---|
| `memo` | 환자가 적은 원문(타이핑·음성). 최대 2000자 |
| `visit_date` | 진료일(ISO). 재방문 날짜 계산의 기준. 없으면 날짜 계산 생략 |
| `clinic` | 병원·과. 앱(1s·1r)이 준다. AI가 만들지 않는다 |
| `labels` (선택) | `{"0":"findings","1":"tests",…}`. **있으면 서버는 LLM을 부르지 않고** 카드만 조립한다. 폰이 분류했거나 1q-2에서 사용자가 고친 라벨 |
| `classify` (선택, 기본 true) | **false면 서버 LLM을 부르지 않고 `sentences`만 돌려준다**(카드는 전부 `unsorted`, `source: "none"`). 폰이 분류할 때 1단계. `labels`가 있으면 무시 |
| `labels_meta` (선택) | labels가 폰 모델에서 왔으면 `{model_id, prompt_version}` → provenance에 기록 |
| `previsit_anchor_id` (선택) | 진료 전 카드의 부위 앵커. 소견 용어의 부위와 **대조만** 한다(same/different) |
| `split_version` (선택) | **앞 응답에서 받은 값을 `labels`와 함께 되보낸다.** 서버 것과 다르면 409 |
| `request_id` | 응답에 그대로 |

응답:

```json
{
  "card": { "card_type": "postvisit", "axes": { "findings": {"status":"filled","value":"위염 초기라고 하셨어요.","evidence":["위염 초기라고 하셨어요."]}, "tests": {...}, "medication_instructions": {...}, "follow_up": {...} },
            "memo": "...", "unsorted": [], "follow_up_date": {"text":"2주 뒤","date":"2026-09-26","approximate":true,"basis":"visit_date 2026-09-12 + 14d"},
            "visit_date": "2026-09-12", "clinic": "서울OO병원 내과", "widening": [], "site_comparison": null, "provenance": {...} },
  "sentences": ["위염 초기라고 하셨어요.", "혈액검사 했고 결과는 다음에 알려준대요.", "약은 2주분이고 커피랑 매운 거 줄이래요.", "2주 뒤에 다시 오라고 하셨어요."],
  "labels": {"0":"findings","1":"tests","2":"medication_instructions","3":"follow_up"},
  "dropped": [],
  "source": "server",
  "usage": {"input_tokens": 0, "output_tokens": 0, "cost_usd": 0},
  "request_id": "r-77"
}
```

## 네 묶음 — 라벨의 뜻

| 라벨 | 담는 것 | 화면 이름을 붙일 때 |
|---|---|---|
| `findings` | 의사가 말한 상태·소견·병명·안심 | 병명은 **환자가 적은 문장 그대로만**. AI가 추론한 병명은 절대 들어가지 않는다 |
| `tests` | 받았거나 하기로 한 검사, 결과 안내 시점 | |
| `medication_instructions` | **처방·복용법에 더해 생활 지시·금지까지.** "커피랑 매운 거 줄이래요", "술 드시지 말라고" 가 여기 들어간다 | **"약"으로만 쓰면 틀린다.** "약·생활 지시" 쪽이 맞다 |
| `follow_up` | 다음 방문 시점·조건 | |

> **`medication_instructions`에 생활 지시가 들어가는 건 이름이 애매한 게 아니라 결정이다.**
> 처음 설계는 6축이었고(#9) 생활 지시가 따로 있었는데, 진료 후 메모 실측에서 그 축이 거의
> 비었고 약 문장과 한 문장에 같이 오는 일이 많았다(`"약은 2주분이고 커피랑 매운 거 줄이래요"`).
> 나누면 한 문장을 쪼개야 하는데 **값이 문장 원문이라 쪼개는 순간 환자 말이 아니게 된다.**
> 그래서 4축으로 접었다(2026-09-07). 화면 라벨을 "약"으로 달면 환자가 생활 지시를 못 찾는다.

- `card.axes.*.value`는 그 묶음 문장들을 ` · `로 이은 **원문**, `evidence`는 문장 목록. AI가 고쳐 쓴 말이 없다
- 묶음에 문장이 없으면 `status: unknown`(메모에 그 얘기가 없었다)
- `unsorted`: 어느 묶음에도 안 들어간 문장. **버리지 않는다.** 1q 화면 하단에 "분류되지 않은 메모"로
- `follow_up_date`: 결정론 계산. `approximate: true`면 "전후"로 표시. 못 읽으면 `null`(앱 달력에서 직접).
  **`classify: false`(문장 분리만)로 부르면 라벨이 없으므로 `follow_up_date`는 항상 `null`이다** —
  폰이 분류한 뒤 `labels`와 함께 다시 부르면 그때 채워진다
- `widening`: 소견 문장의 해부 용어에 부위 병기(설명 아님). `site_comparison`: 진료 전 부위와 같은가(판정 아님)
### `split_version` — 문장 번호가 가리키는 것이 바뀌지 않게

응답에 최상위 `split_version`(예: `"split-v1"`)이 있다. **`labels`를 되보낼 때 같이 보내세요.**

`sentences`의 번호는 라벨의 **주소**입니다. 우리가 분리 규칙을 고치면 같은 메모가 다른
개수·다른 번호로 나뉘는데, 그 배포가 **1p(메모 작성)와 1q-2(라벨 수정) 사이에 끼면** 앱은
예전 번호로 매긴 라벨을 보내고 서버는 새 문장에 그 번호를 붙입니다. 200이 나가고 카드도
멀쩡해 보이는데 내용이 어긋납니다 — 조용히 틀린 카드가 저장됩니다.

| | |
|---|---|
| 값이 같으면 | 평소대로 |
| 값이 다르면 | **409**. `detail`에 `분리 규칙이 바뀌었습니다. 다시 분류해 주세요 (보낸 값 …, 서버 …)` |
| 필드를 안 보내면 | 검사하지 않습니다. 붙이기 전까지는 지금과 똑같이 동작합니다 |

409를 받으면 **`labels` 없이 같은 메모를 다시 보내** 새 `sentences`와 `split_version`을 받으면
됩니다. 재시도로 풀리는 일이라 4xx이고, 규칙과 라벨이 어긋난 상태 충돌이라 409입니다.

우리 쪽 장치: 이름은 사람이 읽도록 손으로 붙이되(로그에 그대로 찍힙니다), **규칙만 바꾸고
이름을 안 바꾸는 일**은 테스트가 막습니다 — 분리 규칙의 지문을 상수 옆에 박아 두고 불일치면
실패합니다. 이름을 안 올리면 409가 안 나고 라벨만 어긋나는데, 그게 이 필드로 막으려던
사고와 정확히 같은 모양이라서입니다.

### 문장 분리 — 한 문장에 두 주제가 오면 나눈다 (`split-v2`, 2026-09-14)

라벨은 **문장당 하나**다. 그래서 한 문장에 두 주제가 있으면 한쪽이 사라진다.

```
"나프록센 500mg 먹으라고 하셨고, 다음 주 화요일에 MRI 찍기로 했어요"
  split-v1  →  한 문장. 약으로 분류되고 MRI가 유실
  split-v2  →  "나프록센 500mg 먹으라고 하셨고" / "다음 주 화요일에 MRI 찍기로 했어요"
```

**연결어미를 전부 자르지는 않습니다.** 기계적으로 자르면 `"아무 말도 안 하시고"` 같은 조각이
생기고, 라벨이 없어 `unsorted`로 떨어집니다 — 문장 수만 늘고 카드는 나빠집니다. 그래서 조건을
겁니다: `-고`·`-며` 뒤이고(인용 `-라고/-다고/-자고`는 제외), **양쪽이 각각 주제 신호를 갖고,
그 주제가 서로 다를 때만** 자릅니다. 하나라도 신호가 없거나 겹치면 두 조각이 같은 묶음으로 갈
말이므로 자르지 않습니다.

| | |
|---|---|
| 자른다 | `"피부염이라고 하셨고 / 연고 처방받았어요"` (소견 + 약) |
| 안 자른다 | `"혈액검사 했고 결과는 다음에 알려준대요"` (둘 다 검사) |
| 안 자른다 | `"약은 2주분이고 커피랑 매운 거 줄이래요"` (둘 다 약·생활 지시) |
| 안 자른다 | `"아무 말도 안 하시고 약만 주셨어요"` (앞이 주제가 아니다) |

원문은 보존됩니다 — 연결어미는 앞 조각에 남기고 글자를 더하거나 빼지 않습니다.

**공백이 없어도 자릅니다**(`split-v3`, 2026-09-14). 실제 사용자는 쉼표 뒤를 안 띄웁니다 —
`"위염 초기라고 하셨고,2주 약 먹고"`가 앱 화면에서 나온 실제 메모이고, 예전 규칙은 이걸 한
조각으로 넘겨 **소견 줄이 통째로 사라졌습니다.** 문장 끝(`.`)도 같습니다(`"하셨음.피검사는"`).
숫자·영문 사이의 점은 문장 끝이 아니므로 `2.5mg`·`example.com`은 그대로 둡니다.

**`split_version`이 `split-v3`입니다.**

### 카드 값 — `value`는 다듬고 `evidence`는 원문

`card.axes.*.value`는 **어미를 정리한 줄**, `evidence`는 **문장 원문 그대로**입니다.
진료 전 카드가 이미 이 구조입니다. 결정론이라 폰·서버가 같은 값을 냅니다.

```
evidence  ["위염 초기라고 하셨고"]        ← 환자가 적은 그대로
value     "위염 초기"                  ← 화면에 그리는 줄
```

| 하는 것 | 안 하는 것 |
|---|---|
| 인용·보고 어미 제거(`~라고 하셨어요` → 뗌) | **동의어 치환**(`피검사` → `혈액검사`) |
| 명령 인용 → 명사형(`줄이라고` → `줄이기`) | **없던 말 추가**(`시행`·`처방`) |
| 평서 인용은 어미 복원(`괜찮다고` → `괜찮다`) | 요약·순서 바꾸기 |
| 끝 구두점·공백 정리 | 숫자·단위·약 이름 손대기 |

**규칙에 없는 어미는 그대로 둡니다.** 어색하게 남는 쪽이 어간을 잘라먹는 쪽보다 낫습니다
(`"오늘은 스케일링만 했음"`은 그대로 갑니다). 이것이 "설명문을 생성하지 않고 인용한다"가
지켜지는 방식입니다.

재방문 줄만 틀을 씁니다: `follow_up_date`가 잡히면
`value = "{메모에서 뽑은 말} ({M월 D일}[ 전후])"` — 예: `"2주 (9월 26일 전후)"`.
**우리 필드끼리 조합하는 것**이라 새 문장을 만드는 것이 아닙니다. `approximate`면 "전후"가
붙습니다(안 붙이면 카드가 그 날짜로 못박은 것처럼 읽힙니다).

### 재방문 날짜 — 기간이 앞 절에 있을 때

`"2주 약 먹고 다시 오라고 했어요"`처럼 **"뒤"·"후" 없이** 말하는 일이 많습니다. 기간만 보고
잡으면 안 됩니다(그 2주가 약 기간일 수 있습니다). 그래서 **같은 절에 다시 온다는 말이 있을
때만** 기간을 재방문으로 읽습니다.

절이 갈려서 `"2주 약 먹고"` / `"다시 오라고 했어요"`가 되면(서로 다른 묶음이라 갈리는 게
맞습니다) 재방문 절에 기간이 없습니다. 이때만 **바로 앞 절이 약·기간 말이면** 그 기간을
씁니다. **여기가 유일하게 추론이 들어가는 자리**라 `basis`에 남깁니다:

```json
"basis": "앞 절 '2주 약 먹고'의 기간을 씀 · visit_date 2026-09-12 + 14d"
```

- `sentences`·`labels`는 **1q-2 수정 화면의 입력**이다. 사용자가 라벨을 바꾸면 같은 엔드포인트에 `labels`를 넣어 다시 부른다(LLM 없음, 즉시)

## 흐름

```
1p 메모 작성 ─▶ 백엔드 ─{memo, visit_date, clinic}─▶ AI ─▶ 서버 LLM 분류 → 카드
1q 결과 표시 ◀─ card, sentences, labels ─┘
1q-2 수정   ─▶ 백엔드 ─{memo, labels(고침)}────▶ AI ─▶ LLM 없이 카드 재조립
1r 일정     ◀─ card.follow_up_date ─┘
```

온디바이스(2026-09-09 결정, #35): ① `classify: false`로 불러 `sentences`를 받는다(LLM 0) → ② 폰 모델이 문장에 라벨 → ③ `labels` + `labels_meta`로 다시 불러 카드 조립(LLM 0). 폰이 실패하면 `classify` 없이 불러 서버 Terra 폴백. 문장 분리는 항상 서버가 한다(폰·서버가 같은 번호를 가리키게).

| 502 | 분류기 출력 파싱 실패 | 같은 요청 1회 재시도 |
| 503 | 모델 지출 상한 | 운영 알림 |

## 지키는 선
- 값은 문장 원문. 요약·정리·설명 없음. 병명은 환자가 적은 그대로만
- 약 용법·검사 결과를 일반 지식으로 채우지 않는다(분류만)
- 날짜는 LLM이 아니라 계산. 병원·과는 앱이 준다

## 근거·수치
- 분류 정확도(Qwen3-1.7B, 20메모/69문장): 93%, 원문 보존 위반 0 — `evals/RESULTS.md` "챗봇② B1"
- 폰 벡터 34개(`evals/ondevice/`), PC 라벨 정확도 **123/132 = 93.2%**(2026-09-14). `split-v3`에서 기존 33개는 문장이 그대로고 PM24(앱 화면 메모)가 늘었다. `split-v2`로
  PM20의 문장이 3→4가 되고 PM21~23이 추가됐다. 나머지 29개는 문장도 번호도 그대로고,
  재실행해도 저장된 PC 출력과 같은 값이 나오는 것을 확인했다(PM01·PM04)
- 프롬프트 `memo-small-v4`, 출력 스키마 `evals/ondevice/memo_labels.schema.json`(번호 키 객체는 요청별 생성)
