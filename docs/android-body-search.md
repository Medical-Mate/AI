# 부위 폼 검색 — 앱 로컬 구현 명세 (안드로이드 전달)

작성 2026-09-11. 관련 이슈 #35. 계약 문서는 `docs/api-previsit.md`.

앱이 검색을 **서버 왕복 없이 로컬에서** 처리하기로 했다(한 글자마다 호출하므로). 이 문서는 그때
서버와 같은 결과를 내기 위한 규칙과 검증 자료다.

## 넘기는 것 두 개

| 파일 | 크기 | 용도 |
|---|---|---|
| `docs/examples/body-map.json` | 14.7KB (공백 제거 8.6KB) | 데이터. 앵커 9 · 구역 25 · 별칭 122 |
| `docs/examples/body-search-vectors.json` | 38KB | 검증용 기대 결과 165케이스 |

데이터는 `GET /v1/ontology/body-map` 응답과 같다. 앱 자산으로 박아도 되고 첫 실행에 받아서
캐시해도 된다. 갱신 여부는 `ontology_snapshot` 문자열로 판단한다.

## 서버와 일부러 다르게 두는 것

**한/영 자판 오타 복원은 앱에 넣지 않는다**(2026-09-11 결정). `qo`→배, `duvrnfl`→옆구리를
서버는 하고 앱은 하지 않는다. 두벌식 조합 오토마타를 코틀린으로 옮기는 비용이 얻는 것보다 크다고 봤다.

그래서 아래 규칙과 벡터에는 그 기능이 없다. 서버 엔드포인트는 그대로 두므로, 나중에 필요해지면
그때 서버를 부르거나 포팅하면 된다(`src/medimate/ontology/korean_keys.py`, 99줄).

## 매칭 규칙

### 1. 정규화

질의와 후보 문자열 양쪽에 같은 처리를 한다.

- 제거: 공백, 가운뎃점 `·`, 소괄호 `()（）`, 쉼표, 마침표
- 소문자화
- 정규화 후 빈 문자열이면 결과 없음

`허리 옆(옆구리)` → `허리옆옆구리`

### 2. 후보와 점수

대상은 **앵커와 구역만**이다. 각 노드의 `label`과 `aliases`를 모두 후보로 삼고, 그중 가장 높은
점수 하나만 그 노드의 점수로 쓴다.

| 점수 | 조건 |
|---|---|
| 3 | 후보 == 질의 |
| 2 | 후보가 질의로 시작하거나, 질의가 후보로 시작 |
| 1 | 한쪽이 다른 쪽을 포함 |
| — | 그 외는 후보 아님 |

증상·병명은 매칭하지 않는다. 데이터에 없으므로 자동으로 그렇게 된다.

### 3. 정렬

1. 점수 내림차순
2. 같으면 **걸린 후보 문자열이 긴 것**이 먼저 (구체적인 쪽. `왼쪽 아랫배가 아파요` → 아랫배 > 배)
3. 같으면 앵커가 구역보다 먼저
4. 같으면 ID 오름차순

### 4. 앵커에 딸린 구역 붙이기

정렬이 끝난 뒤, **점수 2 이상으로 걸린 앵커**가 있으면 그 앵커의 구역을 목록 뒤에 붙인다.

- 순서는 `body-map.json`의 `zones` 배열 순서 그대로 (디자이너 인체도 배치 순서다)
- 붙는 구역의 점수는 **0**. 직접 매칭과 구분된다
- 이미 목록에 있는 구역은 다시 붙이지 않는다
- **점수 1(부분 포함)인 앵커는 펼치지 않는다.** `전체`가 `머리 전체`·`팔 전체`에 스쳐서 앵커
  넷을 펼치면 결과가 23건이 되고 잘려서 눈·귀만 남는다

`q=다리` → 다리(3) · 허벅지(1) · 무릎(0) · 종아리(0) · 발목(0) · 발(0)

### 5. 상한

- 결과는 최대 **8건**. 현재 데이터에서 8건을 넘는 질의는 없다(테스트로 고정)
- 질의는 300자에서 자른다. 거절이 아니라 자르기 (발화 상한과 같은 값)

## 화면 쪽 참고

- **점수 0 항목**은 "직접 걸린 게 아니라 그 부위 아래 것들"이다. 구분선이나 흐린 색으로 나눠도 되고
  그냥 이어 붙여도 된다. 앱 판단
- **표시 문구는 `body-map.json`의 `label`을 쓴다.** 다른 파일(`anchors3d.json` 등)에도 이름이
  들어 있지만, 이름의 출처는 body-map 하나로 둬야 나중에 이름이 바뀔 때 어긋나지 않는다
- 한글 조합 중간 상태(`옆ㄱ`, `옆굴`, `아랫ㅂ`)는 결과가 0건이 된다. 한 글자마다 검색하면 후보
  목록이 깜빡이므로 **0건이 오면 직전 결과를 유지**하는 쪽을 권한다. 서버도 같은 동작이다

## 검증

`docs/examples/body-search-vectors.json`의 165케이스를 그대로 돌린다. `expect` 배열은
**순서까지** 일치해야 한다.

```json
{
 "q": "다리",
 "expect": [
  {"id": "ANC:014", "matched": "다리",     "score": 3},
  {"id": "SUR:090", "matched": "넓적다리", "score": 1},
  {"id": "SUR:091", "matched": "다리",     "score": 0},
  {"id": "SUR:097", "matched": "다리",     "score": 0},
  {"id": "SUR:101", "matched": "다리",     "score": 0},
  {"id": "SUR:102", "matched": "다리",     "score": 0}
 ]
}
```

`matched`는 어느 후보 문자열에 걸렸는지다. 점수 0인 항목의 `matched`는 그 앵커가 걸린 문자열이다.

케이스 구성: 이름·별칭 156개 전부 + 문장 3 + 여러 앵커에 걸치는 질의 + 결과 0건 케이스
(`무릅` 한글 오타, `감기` 증상, 빈 문자열, 공백만).

규칙이 바뀌면 `uv run python scripts/gen_body_search_vectors.py`로 다시 만든다. 커밋된 파일과
현재 동작이 어긋나면 CI가 잡는다(`tests/test_ontology.py`).
